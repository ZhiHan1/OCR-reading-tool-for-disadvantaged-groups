# 内存与调用优化方案（待确认）

> 本文所有数字都来自本机实测（Python 3.14 / PySide6 / paraformer-large），不是估算。
> 测量脚本在 `%TEMP%\opencode\mem_*.py`，可复现。

---

## 一、现状：内存到底在谁身上

运行中的实例（任务管理器口径）：

| 进程 | 工作集 RSS | 提交 Private | 里面有什么 |
|---|---|---|---|
| `OCR_Reader_Web`（GUI） | 312 MB | **963 MB** | Qt/Chromium + OCR(onnxruntime) + OpenBLAS 预留 |
| `OCR_VoiceWorker`（识别子进程） | 324 MB | **2966 MB** | torch + paraformer-large 权重 + ct-punc |
| `QtWebEngineProcess` | 99 MB | 67 MB | 渲染进程 |
| 合计 | 735 MB | **≈ 4.0 GB** | |

注意 worker 的 324 MB 只是**被 Windows 修剪过的**工作集：一旦刚用完语音，它的 RSS 是 1.75 GB，
所以你在后台看到「2 GB+」主要就是它——而且它**用完永不退出**，一直占着。

### 分阶段实测：钱花在哪

GUI 进程（无 BLAS 限制）：

```
启动                         Private   9.7 MB
+ numpy                     Private 501.4 MB   ← 一项就 491 MB
+ PySide6/QtWebEngine       Private 515.2 MB
+ AppController(core 栈)     Private 563.2 MB
+ OCR 预热完成               Private 629.3 MB   ← OCR 模型 65 MB
```

worker 进程：

```
+numpy                      Private  501.8 MB
+torch 导入                  Private  674.1 MB
+funasr 导入                 Private 1383.3 MB   ← funasr 额外拉进 scipy.signal
加载 paraformer+ct-punc      Private 2862.8 MB
推理后                       Private 2865.7 MB
del 模型 + gc                Private 2740.4 MB   ← 只回收 125 MB！
```

### 三个关键结论

**1）OpenBLAS 白吃了 900 MB —— 每个进程**

OpenBLAS 按「CPU 核数」预留缓冲，每个线程 32 MB（官方文档明确写了）。本机 16 核：

| 配置 | numpy 导入后 | scipy.signal 再加 | 合计 |
|---|---|---|---|
| 默认（16 线程） | 501 MB | +532 MB | ≈ 1033 MB |
| `OPENBLAS_NUM_THREADS=2` | 51 MB | +81 MB | 132 MB |
| `OPENBLAS_NUM_THREADS=4` | 116 MB | — | ≈ 197 MB |

事实验证：`import numpy` 之后 RSS 只有 30 MB，但提交了 501 MB —— 典型「占了地址/提交空间但没摸过」。
我们的推理用的是 torch（自己一套线程池）和 kaldi-native-fbank（C++，不走 BLAS），numpy BLAS 基本用不上。

**2）把 BLAS 限到 4 线程，速度不变**

| BLAS 线程 | 模型加载 | 单次识别（3s 音频） | Private |
|---|---|---|---|
| 16（默认） | 10.9 s | 0.245 s | 2863 MB |
| 2 | 10.7 s | 0.318 s（+30%） | 2090 MB |
| **4** | 10.5 s | **0.256 s（+4%）** | **2089 MB** |

选 4：省 773 MB，延迟差异在噪声范围内。torch 线程数（intra=8）测过 8/4/2，内存和速度都无变化，**不动**。

**3）进程内卸载模型是无效的**

`del model + gc.collect()` 只回收 125 MB（funasr 内部还留着引用/缓存）。
**要真正回收 2 GB，只能结束 worker 进程。**

### 顺带排除掉的选项

| 选项 | 实测/资料结论 | 结论 |
|---|---|---|
| 换 SenseVoice-Small 省内存 | 反而更大：RSS 2283 MB / 提交 2781 MB，加载 15 s | 不换 |
| `EmptyWorkingSet` 修剪 | 只掉工作集，提交一点不减（实测 2740→2740） | 不做 |
| Chromium `--single-process` | 仅调试用，不稳定 | 不做 |
| Chromium `--process-per-site` | 现在只有 1 个渲染进程，收益≈0 | 不做 |
| torch 线程数 | 内存/速度均无变化 | 不动 |

## 二、优化方案（按收益排序，逐项可独立回滚）

### P0-1 限制 BLAS 线程（省 ≈ 770 MB/进程）

新增 `utils/env_limits.py`（不导入任何重库）：

```python
def apply_runtime_limits():
    """必须在 numpy / scipy 导入之前调用。"""
    for key in ('OPENBLAS_NUM_THREADS', 'OMP_NUM_THREADS'):
        os.environ.setdefault(key, str(threads))   # threads 默认 4，可被外部覆盖
```

调用点（都在 numpy 导入之前）：

| 文件 | 位置 |
|---|---|
| `web_entry.py` | 第一行（`bootstrap` 之前） |
| `voice_worker_entry.py` | 第一行 |
| `qt_web/main.py` | `sys.path.insert` 之后、`core.config_manager` 之前（开发态 `run_web.ps1` 直接跑 `-m qt_web.main`，不经过 bootstrap） |

线程数写入 `defaults.yaml` / `config.yaml`：`performance.blas_threads: 4`（0 = 不限制，交回系统默认）。

- 预期：GUI 963 → ≈ 578 MB；worker 2966 → ≈ 2193 MB
- 风险：低。已实测识别延迟 +4%（0.245→0.256 s）。用户可在配置里改回 0。
- 验证：`tests/test_asr_quality.py` 全绿 + 实机识别一次。

### P0-2 闲置时结束语音 worker（省 ≈ 2.1 GB）★最大项

现状：`voice_worker.py` 主循环 `while True`，收到 `idle` 之后照样常驻，模型常驻内存。

方案：**worker 自己判断闲置后退出**（单一策略点，GUI 崩溃也不会漏掉）。

```python
# qt_web/voice_worker.py 主循环
idle_since = time.monotonic()
while True:
    msg = commands.get()
    if msg is None: break
    if msg:                                   # 收到命令 → 重置计时
        idle_since = time.monotonic()
        ...原有处理...
    elif pipeline.is_idle() and time.monotonic() - idle_since > idle_exit:
        send('exiting', reason='idle')        # 先告知 GUI，再退出
        break
    pipeline.tick()
    time.sleep(0.02)
```

配置：`asr.idle_exit_seconds: 300`（5 分钟；`0` = 常驻不退出，恢复当前行为）。

GUI 侧配套（`qt_web/voice_session.py`）：

- `_finished()` 现在把文案改成「语音进程已结束，按住说话可重试」——闲置退出时用户会莫名其妙看到这句。改为统一「就绪 · 松开自动识别」，只有**非 idle 阶段**意外退出才提示异常。
- 保留现有 `_discard()`，用于错误/超时场景。

代价与缓解：

- 冷启动一次识别要重新加载模型：**实测 10.9~14.2 s**（paraformer-large，859 MB 从磁盘读）。
- 缓解 1：5 分钟窗口内连续使用不受影响；
- 缓解 2：加载期间已有「正在准备本地识别模型…」提示，可补一句「约 10 秒」；
- 缓解 3：想常驻就把 `idle_exit_seconds` 调大或设 0（比如开会/录课期间）。

- 预期：闲置时 worker 直接消失 → 省 2.1 GB（提交内存最大的一笔）
- 风险：中低。要保证 `is_idle()` = 未录音、`pending == 0`、`not ending`。竞态由现有心跳/看门狗兜底。
- 验证：识别 → 等 5 分钟 → 任务管理器确认进程消失 → 再识别一次能正常冷启动。

### P0-3 OCR 预热改为按需（省 ≈ 65 MB，启动快 0.3 s）

现状：`AppController.__init__` 无条件起后台线程 `ocr_service.warmup()`，启动即加载 onnx 模型（+65 MB 提交 / +74 MB 工作集）。
`import rapidocr` 本身还要 334 ms。

改为配置驱动：`ocr.warmup: lazy`（默认）| `startup`（当前行为）。

- `lazy`：不预热，首次识别时加载（首次点功能1多 0.3~1 s）
- 收益不大但零风险，且让「启动即占内存」的观感变好

### P1-4 翻译 GGUF 常驻时间收紧（省 1.4 GB，仅在使用翻译后）

- 现状：`TranslationService._idle_timeout = 300` 秒
- 改为 60 秒（可配 `translation.idle_unload_seconds`），并在窗口隐藏到托盘时立即 `unload_model()`
- 前提验证：llama.cpp 用 mmap 加载权重，`unload` 后工作集应能被系统回收 —— **实施前先实测一次**（翻译一次 → unload → 看 RSS）
- 风险：低。下次翻译重新加载 GGUF 需要几秒

### P2-5 代码压缩与调用优化（不改行为）

| 项 | 现状 | 做法 | 收益 |
|---|---|---|---|
| 删除 `_backups/` | 8 份整树快照，含 8 份重复 `qt_web/`、`core/` | 只留最新一份打包前快照，其余删 | 仓库 −0.7 MB、消除误导 |
| 旧 UI 入口 | `main_modular_win11.py`(3332 行)、`qt_main.py`(1242 行)、`ui/`(0.3 MB) | 确认只发 Web 版后移到 `legacy/` 或删除（不进包，纯整洁性） | −4500 行 |
| `AppController` 懒构造 | 9 个控制器 + 去重服务全部在启动时构造 | 改成 `@property` 按需创建 | 启动 −约 0.2 s；Web 版根本用不到 `voice_input`（识别走子进程） |
| `api.py` 3 s 轮询 | 每 3 s `registry.scan()` + `ModelManager.scan()` + 全量 JSON（实测首轮 30 ms，之后 2.5 ms） | 页面不可见时降到 30 s，或只在设置/语音页活跃时扫 | CPU/IO 微降，日志更干净 |
| 五个扫描控制器 handler 重复 | func1/func2/func3/manga/game 各自一份几乎相同的模板 | 抽 `_scan_mode_handler(mode)` 工厂 | −150~200 行 |
| 前端合并压缩 | 19 个 JS + 6 个 CSS，共 205 KB，逐个 `<script>` 加载 | 可选合并成 1 js + 1 css | 对内存几乎无影响，**建议不做**（会牵动 `?v=` 缓存版本） |

### 不做的（避免过度工程）

- 不引入进程池/工作线程池重构
- 不把翻译也搬进子进程（除非 P1-4 实测证明 unload 无效）
- 不做 JIT/minify 构建链

### 6.6 多屏框选（混合 DPI）修复

**现象**：多块缩放比例不同的屏幕（如 125% 主屏 + 200% 副屏）下，框选画面局部放大、OCR 截取区域与选框不一致。

**根因**（实测证据）：
1. Qt6 下用**单一窗口铺满整个虚拟桌面**时，Qt 按窗口主要所在屏的 DPR 重新解释 geometry——`setGeometry(-1920,0,3456,960)` 实际落成 `(-2160,0,2160,600)`，遮罩根本没铺满两块屏。这与 flameshot 在 Qt6 多屏修复（PR #4535）中记录的行为一致，业界结论是**必须每块屏一个窗口**。
2. `QScreen::geometry()` 在 Qt6 返回**混合坐标**：原点是 native 物理像素、尺寸是逻辑像素（native/dpr）。因此「逻辑原点 × DPR = 物理原点」的推算在负坐标副屏上必然出错（如副屏逻辑 -1920 @200%，物理原点仍是 -1920 而非 -3840）。物理原点必须通过 Win32 `MonitorFromWindow` + `GetMonitorInfoW` 查询。
3. `QGuiApplication.primaryScreen().grabWindow()` 抓虚拟桌面时，pixmap 的 DPR 按主屏计算，混合 DPI 下与窗口逻辑尺寸不匹配，绘制被放大。

**修复**（`qt_ui/selector.py` 重写）：
- 每块屏一个 `_ScreenShade` 无边框窗口，geometry = 该屏 `QScreen.geometry()`（单屏范围内 Qt 几何可靠）；
- 底图 = 各屏 `grabWindow(0)` 整屏抓取（Qt 官方推荐方式），pixmap DPR = 该屏 DPR，绘制 1:1 无变形；
- 物理原点在窗口落屏后用 `MonitorFromWindow(winId)` + `GetMonitorInfoW` 查询（真实值，非推算）；
- 返回 bbox 直接采用 Win32 `GetCursorPos` 物理坐标（与 PIL `ImageGrab` 同语义），不再经过任何逻辑↔物理换算；`GetCursorPos` 不可用时才用「本屏物理原点 + 局部坐标 × 本屏 DPR」兜底。

**验证**（`tests/test_selector.py` 6 个用例 + 坐标注入式结构相关性对比）：
- 主屏(125%)：bbox 逐像素一致，画面相关度 0.955；
- 副屏(200%)：bbox 一致，相关度 0.928；
- 跨屏框选：bbox 一致，两屏各自交集部分相关度 0.986/0.928；
- 实机渲染截图确认遮罩铺满两屏、选框位置正确、框内亮/框外暗正常。
- `tools/smoke_gui` 全步骤通过（`screenshot_selector` 适配器正常）。

**后续补修（框选后无反应）**：重写时漏了 `QApplication` 导入，`select()` 在
`QApplication.activeWindow()` 处抛 `NameError`，被 `QtSelectorAdapter` 捕获后
返回 `None`，界面表现为「框完什么都没发生」。同时 `_stop_loop()` 原来是
「先关闭遮罩窗口 → 再 `loop.quit()`」，窗口销毁会在鼠标松开事件处理途中
拆掉局部事件循环，也会让 `select()` 提前返回 `None`；已改为
「先 `loop.quit()` → 再隐藏遮罩」。

教训：此前所有验证都手工构造遮罩窗口、直接调 `on_press/on_release`，
**绕过了 `select()` 这个真实入口**，所以没发现。新增 `tests/test_selector.py`
专门守入口（真实调用 `select()`），并把「回退导入后测试必须 FAIL」验证了一遍。


### 6.5 已知取舍

- 闲置 5 分钟后再用语音，需要重新加载模型（实测 11~14 s），界面上会显示「正在准备本地识别模型…」。
- 频繁点功能1/功能2 时，OCR 引擎首次加载约 0.8~1.2 s（换来启动时省下约 90 MB）。
- Chromium 渲染进程内存无法通过以上手段降低。
